## 二、这三条事实推翻了此前两个核心结论

### 推翻结论 1：「服务端不下发流」

**原结论**：checkLive 返回 40018 时无任何媒体字段，故服务端硬拦。
**推翻依据**：F1 证明免费时段能正常观看 → checkLive 成功时**必然下发了流地址**。
**修正**：40018 只是「时段锁」的拒绝码，不代表系统架构无媒体下发能力。

### 推翻结论 2：「第二道门槛是 VIP」

**原结论**：timeCharge 返回 1008 = VIP 门槛。
**推翻依据**：F2 证明付费房能预览 30 秒 → 说明流已下发，30 秒后被切断。
**修正**：第二道门槛是**票务/时长控制**，与 VIP 无关。

## 三、修正后的完整业务模型（三套独立机制）

| 机制 | 层级 | 判定条件 | 表现 | 对应接口/码 |
|---|---|---|---|---|
| **① 时段锁** | 账号级 | 20:00–01:00 且 `vip.type==0` | 全站弹 VIP 窗 | `Live.checkLive` → `40018` |
| **② 房间票务** | 房间级 | `type==2` 且未购票 | 预览 30 秒后停止 | `Live.roomCharge` / 后续切断 |
| **③ 时长轮询** | 会话级 | 周期计费校验 | 继续 / 暂停 | `Live.timeCharge`（60 秒）→ `1008` |

**三者互不替代，不可互相推导。**

## 四、新假设（尚未验证，最高优先级）

### H1：时段锁依赖客户端上报的 header timestamp

**观察到的请求结构**：
```
GET /appapi/?service=Xxx.yyy&uid=...&token=...&signplus=<64hex>
X-App-Version: 3.9.2.5
timestamp: <10位秒级>
X-App-Source: android
```

| 关键点 | 说明 |
|---|---|
| `signplus` 位置 | URL 查询参数 |
| `timestamp` 位置 | HTTP header |
| 物理分离 | 二者不在同一层 |

**假设内容**：服务端用 header 中的 `timestamp` 判断时段；`signplus` 只对 URL 参数签名，不覆盖 header。

**若成立**：改 header timestamp 即可绕过时段锁，且不影响签名验证。

**若实测结果为签名错误**：说明 timestamp 参与签名，需 HMAC 密钥（此路终止）。

**若实测仍返回 40018**：说明服务端使用自身时间，客户端时间不可控（此路终止）。

### H2：破解版「默认 VIP」的三种可能解释（按概率）

| 解释 | 依据 | 可验证性 |
|---|---|---|
| 改客户端时间/时间戳 | 与 H1 一致 | 高（E6 实验） |
| 内置 VIP 账号 uid/token | 服务端查库放行 | 中（需账号数据，不做） |
| 旧版服务端无此限制 | 破解时服务端未上线该策略 | 低（无法验证） |

**优先验证 H1。**
