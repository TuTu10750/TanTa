在 Andarium 安卓虚拟机里跑探他 App，用 Frida 抓它发往本地 netshield 代理的明文 HTTP，拿到真实 API 域名 + `/appapi/home/index` 返回结构，再在 Rex 里复刻。

## 今晚做的步骤

1. **查工具**：`adb --version & python --version & frida --version` —— 三个全在。
2. **连 ADB**：`adb connect 192.168.1.11:5555` —— 连上了。
3. **查 frida-server**：`frida-ps -U` 能列进程，说明 server 活着；但 `adb shell ps -A | findstr fs` 和 `findstr frida` 都找不到它（进程名不叫 fs，ps 里看不到）。
4. **以 root 重开 frida-server**：`adb shell su -c "/data/local/tmp/fs &"` —— 没输出就是成功了（已在跑会报 Address already in use）。重开后 server PID 2543。
   - 背景：店里那次 server 是普通用户跑的，attach 报错 "need Gadget to attach on jailed Android"；这次以 root 跑，attach 成功，没再报这个错。
   - 注意：中途 `frida-ps -U` 有一次卡住没反应，是手机切出了 Andarium、虚拟机暂停了；Ctrl+C，切回 Andarium 前台，再跑就好了。
5. **确认探他在跑**：`frida-ps -U` 里看到 `2197 探他`。
6. **v4 attach**：`frida -U -p 2197 -l D:\浏览器\tanta-hook-v4.js` —— attach 成功，所有 hook 都装上了（connect/getaddrinfo/send/recv/close）。刷了两分多钟首页。
7. **v5 attach**：v4 抓不到数据后，写了 v5（加 hook sendmsg/recvmsg/write/read）。v4 的 cmd 窗口 Ctrl+C 停不掉（日志刷太猛），直接关窗口重开一个，再跑 `frida -U -p 2197 -l D:\浏览器\tanta-hook-v5.js` —— attach 成功，所有 hook 都装上了。

## 关键发现

### 1. 本地代理端口是 40429（已确认）

v4 和 v5 两轮，2 分多钟里抓到 **100 多个** `[connect-lo]`，全部是 `127.0.0.1:40429`。这就是 netshield 在运行时的本地端口（`Netshield.getLocalhostPort("n_11000;11000")` 给出的端口，每次启动可能变）。

### 2. 只抓到连接，抓不到任何数据（核心卡点）

- v4：100+ 个 connect，只有 connect，没有一条 `[send-lo]` / `[recv-lo]`。
- v5：在 v4 基础上又 hook 了 sendmsg / recvmsg / write / read，还是只有 connect，没有一条 `[sendmsg-lo]` / `[recvmsg-lo]` / `[write-lo]` / `[read-lo]`。
- 结论：**App 发数据没走 libc 的 send / recv / sendmsg / recvmsg / write / read**。connect 走 libc（所以能抓到），但真正传数据的那条路不在这些函数里。

### 3. 还看到一个外部 IP

两轮都出现 `47.243.154.132:443`（阿里云 IP）。只看到 connect，没看到内容（TLS 密文也看不到）。可能是 netshield 的出站或配置服务器，未确认。

### 4. 排除掉的假设

- 不是 attach 失败：两次 attach 都成功了，hook 全装上了，connect 抓得好好的。
- 不是 App 没跑：探他 PID 2197 一直在跑，刷了两分多钟首页，连接数一直在涨。
- 不是虚拟机暂停：暂停时命令会卡住没反应，这两轮日志一直在刷，说明虚拟机是活的。
- 不是 v4 的回环过滤问题：v4 已经修了这个（v3 才过滤 127.0.0.1），v4/v5 都是全量记 connect、回环全文 dump。

## 结论

- **已拿到**：netshield 本地代理端口 **40429**；frida-server 以 root 跑通了，attach 没问题；家里电脑整套工具链是通的。
- **还没拿到**：真实 API 域名、`/appapi/` 请求内容、响应结构。因为数据没走 libc 的 socket 收发函数，hook 这条路目前看不到明文。
- **最可能的解释**：libnetshield 自己实现了收发（比如直接调 syscall、走 io_uring，或者数据在另一个库/线程里走），connect 只是建连，建连走 libc，传数据不走。

## 下一步（按优先级）

1. **tcpdump 抓回环（最稳）**：在虚拟机里以 root 跑 tcpdump 抓 `lo` 接口（`tcpdump -i lo -n port 40429`），不管 App 用哪个函数发数据，只要是发往 127.0.0.1:40429 的 TCP 包都能抓到，明文 HTTP 直接可见。这是绕开 hook 的办法。
2. **直接 hook libnetshield.so**：找它导出的连接/收发函数（比如它的 send/recv 封装），而不是 hook libc。需要先列出 libnetshield.so 的导出函数。
3. **Java 层 hook**：如果 App 的 HTTP 是 Java 层（OkHttp / HttpURLConnection）发的，hook Java 层的 HTTP 客户端也能看到 URL 和 body。
4. **不建议再做的**：继续加 hook libc 的其他收发函数（sendto/recvfrom 等）—— v4/v5 已经证明这条路没数据，再加也是白试。
